# 分层接口与实验设计

记录日期：2026-10-24

文档性质：执行稿 v0.2（2026-10-24 已确认 A1–A5）。用于确定 Paper P 的软件边界、基线接入方式和实验矩阵。本文档不改变 `03_M0方向冻结记录.md` 已确认的 Paper P 主线和 REMUS 100 主平台；ROS 2、HoloOcean 和 DDPG 都不作为 M1–M5 的前置条件。

## 1. 核心结论

建议采用“端口—适配器”结构，而不是把 ROS 2 或 HoloOcean 放进算法核心：

```text
             任务/语义层（以后可接 VLA、场景图、行为树）
                              ↓ TaskSpec
                     世界模型（oracle 或估计）
                              ↓ PlanRequest
                 全局规划器（Paper P 的核心层）
                              ↓ PlanResult: Trajectory + Certificate + Diagnostics
                       名义制导（LOS/ALOS）
                              ↓ Reference
                  局部规划/安全层（以后可接 DDPG、CBF）
                              ↓ CommandProposal / SafeCommand
                      控制与分配（PID、MPC、舵面/推力器）
                              ↓
                  仿真后端（PVS、MSS、HoloOcean）或真机
```

三条设计原则：

1. **核心算法只依赖 Python 契约**：`numpy`、标准库和项目内 dataclass/Protocol；不导入 `holoocean`、`rclpy` 或 PyTorch。
2. **仿真器和 ROS 2 都是适配器**：替换仿真器、加入局部规划或语义层时，不修改全局规划器内部。
3. **先证明单层可替换，再做系统集成**：先把各层在同一场景、同一评价器下跑通，再谈端到端系统。

## 2. 与 Paper P 及复刻论文的关系

### 2.1 Paper P 的主线不变

Paper P 的核心仍是 `README.md:9` 定义的可恢复性感知三维全局动力学规划。其最小闭环包括：

- `PlanRequest → Trajectory`；
- 海流代价、全艇体扫掠和动力学可行性；
- 可恢复余量、备用机动和证书；
- 与动力学 RRT*、海流感知轨迹优化、动力学规划 + 输入约束 CBF 的强基线对照。

### 2.2 复刻论文的定位

`Three-Dimensional Autonomous Navigation ... Adaptive Line-of-Sight Guidance` 作为**系统基线**，不替代 Paper P：

| 论文模块 | 在我们的架构中 | 用途 |
|---|---|---|
| 改进 PSO 全局航路 | `GlobalPlanner` 的一个实现 | 几何/高度图全局基线 |
| DDPG 局部避障 | `LocalPlanner` 的一个实现 | 局部反应式基线 |
| 3D ALOS | `Guidance` 的共享实现 | 所有规划器共用的跟踪层 |

这三部分必须可以在实验配置中独立开关。不能把“PSO + DDPG + ALOS 整体”直接和一个全局规划器比较，否则无法判断收益来自哪一层。

### 2.3 两条实验线

```text
Paper P 主线：M1 契约 → M2 地图/海流 → M3 几何基线 → M4 REMUS 闭环
              → M5 模型可信性 → M6 恢复证书 → M7 候选规划器 → M8/M9 论文实验

复刻/集成线：F0 快速解析闭环 → F1 HoloOcean 系统骨架 → F2 DDPG 局部基线
              → F3 接入 Paper P 对照
```

F1 可以在 M4 之后并行推进；F2 不阻塞 Paper P 的 M1–M5。HoloOcean 是 E4 的必做高保真主实验，结果进入论文主表；它不作为 M1–M5 的代码前置条件，但必须在 M8/M9 论文结果冻结前完成。

## 3. 分层职责

| 层 | 本阶段是否实现 | 输入 | 输出 | 主要责任 |
|---|---|---|---|---|
| T 任务/语义 | 只留接口，暂不实现 VLA | 指令、目标、风险预算 | `TaskSpec` | 以后接语义规划和行为树 |
| B 世界模型 | 第一版 oracle | 真值地图、海流、艇体状态 | `PlanRequest` / `BeliefState` | 提供地图、流场、能力和不确定性 |
| P 全局规划 | 是，Paper P 核心 | `PlanRequest` | `PlanResult` | 生成轨迹、代价、证书和失败原因 |
| G 名义制导 | 是，先接 ALOS/LOS | `Trajectory` + `State` | `Reference` | 把轨迹变成可跟踪的艏向/深度/速度参考 |
| L 局部规划/安全 | 只留接口，后续接 DDPG/CBF | `Reference` + `LocalObservation` | `ControlProposal` / `SafeCommand` | 局部避障、安全否决和重规划请求 |
| C 控制/分配 | 先用 PVS/HoloOcean 自带控制器 | `SafeCommand` | 推力/舵角 | 执行器约束和跟踪 |
| 运行时监督 | 只留接口 | 健康、偏差、证书失效 | `ReplanTrigger` | 故障、感知退化和重规划 |

层间通信只使用显式对象，不允许“上层直接读下层内部状态”。例如全局规划器不能读取 HoloOcean 的传感器字典，局部规划器不能偷偷读取完整真值地图；训练期特权信息必须通过配置显式打开并记录。

## 4. 核心数据契约

契约文件建议放在 `src/auv_planner/contracts.py`，所有类型可序列化为 JSON 或 NumPy 文件。第一版只定义真正需要的字段，避免制造空抽象。

### 4.1 坐标、时间和单位

- 世界坐标：NED，单位 m；角度 rad。
- 艇体坐标：FRD；所有力矩和速度方向在适配器中转换。
- 四元数：统一 `xyzw`，字段名写明 `quat_xyzw`。
- 时间：核心用秒 `t_s`；外部消息同时保留 `stamp_ns`，仿真时间与墙钟时间分开。
- 所有对象带 `frame_id` 或明确的参考系字段；禁止在不同模块中混用 Unreal、ENU 和 NED。
- HoloOcean、PVS、MSS 的坐标转换必须各有一个帧变换单元测试。

### 4.2 最小对象

| 对象 | 关键字段 | 说明 |
|---|---|---|
| `VehicleSpec` | 长度、直径、质量、速度/加速度限制；可选舵角、舵速和最大 RPM | 平台约束 |
| `State` | `t_s`、NED 位置、`quat_xyzw`、FRD 线速度/角速度 | 统一状态 |
| `WorldSnapshot` | 地图、边界、海流、障碍真值、`stamp` | oracle 第一版 |
| `CurrentField` | `sample(position, t) -> velocity`、误差界 | 均匀流起步 |
| `CapabilitySet` | 可用执行器、剩余效能、故障族、诊断延迟界 | 恢复检查使用 |
| `TaskSpec` | 目标区域/目标点、任务约束、风险预算 | 语义层只输出任务，不输出轨迹 |
| `PlanRequest` | `request_id`、起点、目标、世界、平台、能力、约束、种子、父计划 | 一次规划输入 |
| `PlanResult` | 状态、`Trajectory`、代价、`RecoveryCertificate`、诊断、规划时间 | 一次规划输出 |
| `Trajectory` | `trajectory_id`、时间、状态、控制、clearance、可行性标记 | 所有规划器统一输出 |
| `RecoveryCertificate` | 是否有效、假设、故障集、备用机动、有效时间、无解原因 | 没有证书时必须显式标记 |
| `LocalObservation` | 声呐、局部地图、位姿、速度、健康、`stamp` | 局部规划器输入 |
| `Reference` | 位姿、速度、航向、深度、前馈、有效时间 | 制导层输出 |
| `ControlProposal` | 体坐标加速度、角速度、`stamp`、`valid_until` | 上层运动建议，不是舵面指令 |
| `SafetyContext` | 当前状态、局部障碍、能力集合、证书状态 | 安全层判断依据 |
| `SafeCommand` | 经安全层修正或否决后的控制量、原因、有效时间 | 交给控制/分配层 |
| `ActuatorCommand` | `stamp_s`、`valid_until_s` | 平台无关的执行器命令协议，只约束时间语义 |
| `Remus100ActuatorCommand` | 艉舵角、艉水平舵角、螺旋桨 RPM、`stamp`、`valid_until` | 已分配并限幅的 REMUS 100 具体执行器指令 |
| `SimulationSnapshot` | 同步的 `State`、`WorldSnapshot`、实际执行器状态、诊断量 | 仿真后端一步输出 |
| `EvalResult` | 成功、碰撞、显式越界标志、clearance、路径长度、时间、能量、跟踪误差、恢复指标、失败原因 | 统一评价结果；越界不得从失败原因字符串推断 |

### 4.3 规划状态与重规划协议

`PlanResult` 至少应包含：

```text
status: OK | INFEASIBLE | TIMEOUT | DEGRADED | ERROR
plan_id: str
parent_plan_id: str | None
valid_until_s: float | None
reason: str | None
```

`PlanRequest.reason` 区分 `INITIAL`、`NEW_GOAL`、`OBSTACLE`、`DEVIATION`、`CAPABILITY_CHANGE` 和 `RECOVERY`。这样以后局部规划或运行时监督请求重规划时，不需要改变全局规划器接口。

### 4.4 航点与轨迹的兼容

PSO 只自然输出航点，Paper P 可能输出完整轨迹。不要让 PSO 伪造动力学可行性：

- `PlanResult` 始终包含一个 `Trajectory`；
- 航点型规划器通过 `build_trajectory` 提升为轨迹，并标记 `feasibility="unchecked"` 或 `"tracked"`；
- 只有经过动力学适配器或跟踪闭环检查后，才能标记为 `"kinodynamically_feasible"`；
- 评价器必须保留这个区别，避免把“航点能连起来”误报成“AUV 能执行”。

### 4.5 接口契约矩阵

| 端口 | 生产者 → 消费者 | 坐标与单位 | 时间/失败语义 |
|---|---|---|---|
| `GlobalPlanner` | 任务/世界模型 → 制导/评价 | 输入输出均为 NED/FRD；长度 m，角度 rad | 失败写入 `PlanStatus` 和 `reason`，不抛异常伪造无解 |
| `Guidance` | 全局规划 → 跟踪控制 | 位置和姿态为 NED；体速度为 FRD；前视点沿路径弧长 | `t_s` 是全局仿真时间；进度由当前状态投影决定；非法输入显式报错 |
| `TrackingController` | 制导/安全层 → 仿真后端 | 输出为平台无关的 `ActuatorCommand`；REMUS 100 实现输出 `Remus100ActuatorCommand` | 具体指令必须不超 `VehicleSpec` 限幅；过期或越界必须拒绝 |
| `LocalPlanner` | `LocalObservation` → 局部安全层 | 体坐标加速度/角速度 | 只读取显式观测，不直接访问真值地图 |
| `SafetyFilter` | `ControlProposal` → `SafeCommand` | 与输入相同 | 拒绝时必须有 `reason`，不得静默放行 |
| `SimulatorBackend` | 通用 `ActuatorCommand` → `SimulationSnapshot` | 快照中的状态和世界均为 NED/FRD | 通用协议只表达时间信封；具体后端必须拒绝不属于自己的命令类型。`State.t_s` 与 `WorldSnapshot.t_s` 必须同步，固定步长可重复 |

时间补充约定：

- `Reference.valid_until_s` 表示控制参考的失效时间，控制器不得使用过期参考。
- `Reference.valid_until_s` 必须不早于 `stamp_s`；控制器还必须拒绝未来参考和过期参考。
- REMUS 100 控制器输出的命令有效期覆盖当前控制步；同一状态时间重复调用视为错误。
- ALOS 的 `t_s` 只作为时间戳和海流采样时间；路径推进由艇体在路径上的投影决定，不按 `Trajectory.t_s` 回放。
- PVS REMUS 100 当前只支持水平均匀海流；三维或剪切流必须由适配器明确拒绝，不能静默丢弃垂向分量。

### 4.6 导入与类型边界

接口解耦必须在导入级成立，而不只是在文档上成立：

- `auv_planner/__init__.py` 只做惰性导出；`import auv_planner` 不加载 `contracts`、`guidance`、`planners`、`dynamics` 或任何仿真器。
- `import auv_planner.contracts` 只加载契约模块，不加载制导、规划器、PVS 或 ROS 2。
- 制导层从 `attitude.py` 获取四元数工具，不从 `planners.common` 反向导入规划实现。
- `PvsRemus100Backend` 延迟到 `reset()` 才导入 PVS；PVS、HoloOcean、`rclpy` 和 PyTorch 不得进入核心导入链。
- `ActuatorCommand` 是平台无关的时间信封；REMUS 100 的舵角/RPM 放在 `Remus100ActuatorCommand`。以后接 AUV533 或 HoloOcean 时新增各自的命令类型，不把 REMUS 字段硬塞回通用协议。

运行时 `isinstance(x, Protocol)` 只能检查属性或方法是否存在，不能检查参数签名。签名由静态检查兜底：

```bash
cd "/home/bubble/水下机器人/settled_全局规划器"
../.venv/bin/python -m pytest -q
../.venv/bin/python -m mypy
```

当前 mypy 覆盖 `src/auv_planner` 与 `tests/`，包括 `tests/test_contracts.py` 中的协议一致性样例。导入隔离由 `tests/test_import_guard.py` 在独立 Python 进程中验证，避免测试自身的导入顺序污染结果。

## 5. 端口与目录结构

建议在现有目录基础上渐进式落地，不创建大量空文件：

```text
settled_全局规划器/
  src/auv_planner/
    contracts.py              # State, PlanRequest, PlanResult, ActuatorCommand, ...
    interfaces.py             # GlobalPlanner, Guidance, TrackingController, ...
    attitude.py               # 制导与规划器共享的四元数工具
    current.py                # 均匀流、剪切流
    geometry.py               # 全艇体碰撞与扫掠
    guidance.py               # 3D LOS/ALOS
    control/
      remus100.py             # State + Reference -> REMUS 100 actuator command
    dynamics/
      remus100.py             # PVS REMUS 100 有状态适配器
    planners/                 # A*, RRT*, kinodynamic RRT*, PSO, recoverable
    local/                    # 后续 DDPG/APF/DWA
    safety/                   # 后续 CBF/MPC
    recovery/                 # 备用机动、证书
    evaluation/               # metrics, planning runner, closed_loop, recording
    backends/
      mss.py
      holoocean.py            # 只在适配器内 import holoocean
      ros2/                   # 后期再加，只在适配器内 import rclpy
    experiments/              # M4 场景定义、批量运行、报告
  configs/
    vehicles/
    currents/
    scenes/
    experiments/
  tests/
  scripts/
  outputs/
```

关键接口可以是轻量的 `typing.Protocol`：

```python
class GlobalPlanner(Protocol):
    def plan(self, request: PlanRequest) -> PlanResult: ...

class LocalPlanner(Protocol):
    def act(self, observation: LocalObservation, reference: Reference,
            capability: CapabilitySet) -> ControlProposal: ...

class Guidance(Protocol):
    def guide(self, state: State, trajectory: Trajectory, t_s: float) -> Reference: ...

class SafetyFilter(Protocol):
    def filter(self, proposal: ControlProposal, context: SafetyContext) -> SafeCommand: ...

class TrackingController(Protocol):
    def control(self, state: State, reference: Reference) -> ActuatorCommand: ...

class SimulatorBackend(Protocol):
    def reset(self, scenario: ScenarioConfig, seed: int) -> SimulationSnapshot: ...
    def step(self, command: ActuatorCommand) -> SimulationSnapshot: ...
```

接口不必在第一版就覆盖所有传感器和所有控制模式；但必须保证以后加入局部规划和语义层时，不需要重写 `GlobalPlanner`。

## 6. 实验分级

### E0：契约与单元测试

目标：证明所有算法共用同一套数据，不依赖仿真器。

- 坐标和帧变换往返测试；
- 轨迹时间单调、插值、越界和无效字段测试；
- `PlanResult` 的 OK/INFEASIBLE/TIMEOUT 状态测试；
- 所有规划器通过同一个 CLI 和配置加载；
- 核心包导入时不得出现 `holoocean`、`rclpy`、`torch`、`python_vehicle_simulator`。

验收：同一空场景、同一种子，不同规划器都返回合法 `PlanResult`；失败原因可区分。

### E1：纯规划比较

目标：不接动力学和仿真器，比较全局规划器本身。

对象：

- 直连基线；
- 三维 A*；
- 三维 RRT*；
- 动力学 RRT*/运动基元；
- 改进 PSO（论文的全局层）；
- 海流感知轨迹优化；
- Paper P 候选方法。

指标：规划成功率、规划时间、路径长度、clearance、clearance 分布、海流代价、无解率、恢复余量（若有）。

要求：所有方法使用同一地图、起点、目标、海流、分辨率、计算预算和随机种子。PSO 只作为几何基线，不能被称为完整动力学规划。

### E2：PVS 闭环

目标：检验“规划器差异”和“跟踪器差异”是否被混在一起。

统一条件：

- 同一 REMUS 100 PVS 模型；
- 同一 ALOS/LOS 和深度/航向控制器；
- 同一海流输入；
- 同一轨迹后处理和评价器。

对照：

- 几何 A* + 统一跟踪器；
- 动力学路径 + 统一跟踪器；
- PSO + ALOS/论文式跟踪器；
- Paper P 候选轨迹 + 统一跟踪器。

指标：跟踪 RMSE、最小 clearance、碰撞、约束违反、能耗、时间、重规划次数。

M4.1 已建立首个控制基线：固定 `dt=0.02 s`、1.5 m/s、统一 ALOS 和 REMUS 100 跟踪器，记录横向/垂向 RMSE、舵角/舵速、RPM、饱和比例、约束违反、完成时间和逐样本日志。当前只用于判断跟踪器是否会吞掉规划差异，不在控制器标定前设置论文成功阈值。复现入口为 `scripts/run_m4_closed_loop.py`，摘要见 `02_执行计划.md`。

### E3：PVS/MSS 模型可信性

目标：防止规划结果建立在错误的动力学模型上。

场景：直航、阶跃舵、zigzag、定深/定航向、均匀流、深度剪切流。记录参数来源、舵面符号、单位、步长和控制器差异。

验收：关键状态量在预设阈值内；不通过时暂停 Paper P 论文级实验，先修模型或跟踪接口。

M5-A/M5-B 已完成（2026-10-25）：PVS 与 MSS 在 15° 公共舵限、native 质量和密度下完成导数、开环操纵、zigzag、定深/定航向、均匀横流与深度剪切流对照。平静水导数最大相对差 5.34%，深度剪切流 6.30%，横向流 24.94%；开环归一化末端差不超过 1.61%；六个闭环场景全部完成、无约束违反，完成时间差不超过 0.14 s，共同样本轨迹 RMS 不超过 0.089 m；Euler 0.02 s 收敛误差不超过 0.092%。阈值与 8 个冻结场景见 `02_执行计划.md`；用户已于 2026-10-25 确认冻结，M5 证据门关闭。

### E4：HoloOcean 必做主实验

目标：产出论文中的高保真闭环主结果，同时验证跨仿真器接口。不要一开始追求论文中的百分比，也不要用 HoloOcean 替代 PVS/MSS 的模型可信性检查。

第一版配置：

- `TorpedoAUV` 或 `CougUV` + Fossen torpedo 模型；
- 自定义 scenario；
- PSO 航点 + 3D ALOS + 深度/艏向 autopilot；
- 均匀/慢时变海流；
- 少量静态/动态障碍；
- `ImagingSonar` 或自建 13 扇区观测；
- 不用 HoloOcean 从零训练 DDPG。

先跑一个 headless smoke test 和 3 个场景 × 3 个种子；确认仿真吞吐、重置确定性、帧变换和传感器时间戳后，冻结主表场景集。主表初步规模为 6 个场景 × 10 个配对种子；若关键配置方差过大，再扩展到 30 个种子，不能在看到结果后挑选种子。HoloOcean 主表在 M8/M9 前完成，但不阻塞 M1–M5 的代码开发。

E4 主表建议拆成两张，不能把不同层的变化混成一张表：

| 表 | 比较对象 | 固定条件 | 主要指标 |
|---|---|---|---|
| H1 全局层主表 | A*、改进 PSO、动力学 RRT*、海流感知轨迹优化、动力学规划 + CBF、Paper P | 同一 HoloOcean 场景、海流、种子、ALOS 跟踪器和控制后端 | 成功率、碰撞、全艇体 clearance、路径长度、能耗、规划时间、恢复成功率、证书覆盖率 |
| H2 局部层主表（条件性） | DDPG、APF/DWA、CBF 等局部方法 | 固定同一条全局轨迹和制导层 | 碰撞、最小距离、跟踪误差、控制努力、重规划次数 |

H2 只有在 DDPG 完成后才进入主表；如果 DDPG 继续后置，首篇只报告 H1，并明确局部层没有完成该对照。HoloOcean 主表与 PVS 主表分开展示，不能合并统计，也不能用 HoloOcean 结果替代 PVS/MSS 的模型验证。

### E5：Paper P 决定性实验

目标：回答恢复约束是否有独立价值。

对照组至少包括：

- 动力学规划；
- 动力学规划 + 输入约束 CBF；
- 海流感知轨迹优化；
- Paper P 候选方法；
- 恢复约束关闭的消融版本。

压力轴：海流强度、障碍密度、航速、故障族、诊断延迟、执行器剩余能力。

指标：成功率、碰撞、最小全艇体 clearance、约束违反、路径长度、时间、能量、恢复成功率、证书覆盖率、无解率、保守性—安全性 Pareto。

验收：相同信息和计算预算下，候选方法与强基线可比；若没有可重复收益，触发 Paper P 的 No-Go 记录。

### E6：ROS 2 集成冒烟测试（可选）

目标：证明分层接口可以被外部系统调用，而不是把算法迁移到 ROS 2。

- 只启动一个规划动作服务器和一个状态/轨迹发布器；
- 使用同一配置，通过 ROS 2 调用一次 `plan`；
- 比较 Python 直连和 ROS 2 适配器输出的轨迹、代价和证书；
- 论文主实验不依赖 ROS 2；ROS 2 只做集成冒烟测试。

验收：ROS 2 适配器不改变规划结果；仿真时间、帧 ID、消息时间戳可追踪。

## 7. 实验矩阵与规模

第一轮冻结 6–9 个场景，避免一开始铺得太大。建议维度：

| 维度 | 取值 |
|---|---|
| 海流 | 无流、均匀流、深度剪切、慢时变、流 + 模型误差 |
| 障碍 | 稀疏、走廊、峡谷、门框、动态横穿 |
| 航速 | 低速、巡航、高速（REMUS 100 约束内） |
| 故障/延迟 | 无故障、执行能力下降、诊断延迟 0.5/1/2 s |
| 信息 | oracle 地图起步；后续才加入估计地图 |

建议规模：

- E1：6–9 场景 × 5–7 方法 × 20 种子；
- E2：4–6 场景 × 3–5 方法 × 10 种子；
- E3：固定操纵试验，先少量工况，再扩展；
- E4：3 场景 × 3 种子做 smoke/吞吐测试；主表初步 6 场景 × 10 配对种子，关键配置再扩到 30 种子；
- E5：每组先 10 个调试种子，稳定后扩展到 30–100 个独立种子；
- 所有失败运行都保留，不能只保存成功轨迹。

统计要求：同场景配对种子、bootstrap 95% 置信区间、效应量、失败样本和超时率；不要只报均值，不要事后挑选有利种子。

## 8. 基线组合规则

把论文的系统拆成可组合组件，而不是一个不可拆的“黑盒基线”：

```text
全局层：改进 PSO / A* / RRT* / 动力学 RRT* / Paper P
制导层：LOS / 3D ALOS / 统一 PID 跟踪
局部层：无 / DDPG / APF / DWA / CBF
控制层：PVS 控制器 / HoloOcean autopilot
```

实验必须明确当前比较的是哪一层：

- 全局层比较：固定制导、局部层和控制层；
- 局部层比较：固定全局轨迹和制导层；
- 系统比较：明确说明同时改变了哪些模块，不能把系统收益归因于单个算法。

论文的 DDPG 忠实版本只有“纵向加速度 + 艏摇角速度”两个动作；如果后续扩展俯仰/深度动作，必须标记为我们的扩展，不能称为原论文复现。

## 9. ROS 2 决策

### 9.1 当前结论

**第一版不把 ROS 2 作为依赖，也不把 ROS 2 消息作为内部契约。**

原因：

- Paper P 当前是规划算法研究，主要实验是单进程、固定种子、批量跑；
- HoloOcean 官方提供 Python API，直接适配更简单；
- ROS 2 会引入构建系统、DDS、节点生命周期、时间同步和消息版本问题；
- 现有 ROS 2 社区 HoloOcean 桥的成熟度和维护度有限，不能作为论文基础设施的唯一依赖；
- 先做 ROS 2 会让单元测试和算法迭代变慢。

模块化来自清晰接口，不来自是否使用 ROS 2。

### 9.2 什么时候加

满足以下任一条件后再加：

1. 需要与 DAVE、真实 AUV 或其他 ROS 2 节点联调；
2. 需要多进程/远程运行，并已确认仿真时间同步方案；
3. 要把系统作为学位论文集成演示或开源 benchmark 发布；
4. Python 直连版本已经通过 E0–E3，不想让 ROS 2 阻塞算法结论。

### 9.3 加在哪里

只放在 `backends/ros2/` 和独立 ROS 2 包中：

- `uw_interfaces`：`PlanRequest`、`PlanResult`、`RecoveryCertificate`、`Reference`；
- `uw_planning_ros`：调用现有 `GlobalPlanner`，不复制算法；
- `uw_sim_bridge`：HoloOcean/PVS 与 ROS 2 的适配；
- `uw_eval_ros`：记录和诊断。

建议优先使用标准消息：

- `nav_msgs/Path`：航点兼容；
- `trajectory_msgs/MultiDOFJointTrajectory`：三维轨迹；
- `diagnostic_msgs/DiagnosticArray`：健康、证书失效和降级状态；
- `tf2`：坐标系和帧变换；
- 自定义 action 只在需要提交长时间规划任务时使用。

不要把 `RecoveryCertificate` 塞进普通 `String` 后就当作正式协议；如果 ROS 2 成为对外接口，证书应有单独 schema 或单独消息，并带版本号。

## 11. 可复现性与记录

每次实验至少保存：

```text
outputs/<run_id>/
  manifest.json       # git commit, config hash, seed, versions, scenario
  config.yaml         # 完整实验配置
  metrics.csv         # 结构化指标
  summary.json        # 聚合统计和置信区间
  events.jsonl        # 重规划、故障、证书失效等事件
  trajectories/       # 小型轨迹 npz；大结果放外部存储
```

必须记录：

- 规划器名称、版本、配置和随机种子；
- 地图、海流、场景和车辆模型版本；
- 是否使用 oracle 信息、特权奖励或完整真值障碍；
- 规划计算预算和超时策略；
- 仿真时间、墙钟时间和 tick 数；
- 失败原因，不能只记录成功样本。

## 12. 接口验收标准

- [ ] 任意 `GlobalPlanner` 都能通过同一 `PlanRequest` 调用并返回 `PlanResult`。
- [ ] 航点型方法能通过 `TrajectoryBuilder` 接入，但不会被误标为动力学可行。
- [ ] 更换制导器、局部规划器或仿真后端时，不需要修改全局规划器代码。
- [ ] 局部规划器只能看到 `LocalObservation`，不能默认读取真值地图。
- [ ] 证书无效、超时和无解都能被明确记录，不能伪造安全。
- [ ] 同一种子在同一后端、同一配置下可重复得到相同结果。
- [ ] PVS、MSS、HoloOcean 的坐标和单位通过对照测试。
- [ ] ROS 2 适配器可以把同一计划原样传出，不重新实现规划逻辑。
